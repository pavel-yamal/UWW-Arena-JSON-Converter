# Mercure в UWW Arena: что это, зачем и почему таймер может потребовать его

## Что такое Mercure

**Mercure** — открытый протокол «сервер сам присылает обновления клиенту» (push), из экосистемы Symfony
(Arena написана на Symfony). Устроен так:

```
 Arena (сервер)  ──публикует событие──►  Mercure Hub  ──поток SSE──►  подписчики
  «счёт 3:1»                           (/.well-known/mercure)       табло, ТВ-графика,
  «таймер 1:35»                                                     наш сервис
```

- **Hub** — отдельный HTTP-эндпоинт (обычно `https://<arena>/.well-known/mercure`), раздающий события.
- **Топик (topic)** — «канал», на который подписываются, например конкретный ковёр или схватка.
- **SSE (Server-Sent Events)** — одно долгое HTTP-соединение, в которое сервер дописывает события
  по мере их появления. Не WebSocket, обычный HTTP, сквозь прокси проходит нормально.
- **JWT-токен подписчика** — пропуск: какие топики разрешено слушать.

## Как это видно в Arena API

В спецификации (`arena-api.json`) есть явные следы:

| Метод | Что говорит |
|---|---|
| `GET /api/json/scoreboard/mercuretoken/{sportEvent}/{localClient}` | выдаёт Mercure-токен подписчика для **табло** конкретного турнира и клиента |
| `GET /api/json/client/local`, `/client/trusted` | «локальные клиенты» Arena — тот самый `{localClient}` для токена |
| `GET /api/json/arena/current-event` (описание) | упоминает **UDP-шлюз** с «листенерами на каждый ковёр» — ещё один канал живых данных от табло |

То есть табло Arena получает данные **не опросом REST**, а подпиской на Mercure.
Схем событий (какие топики, какие поля) в спецификации нет — их нужно посмотреть на живой системе.

## Почему вопрос встаёт именно из-за таймера

| Данные | Как часто меняются | Хватает ли REST-опроса раз в 1 с |
|---|---|---|
| ФИО, страна, весовая категория | раз за схватку | да |
| Счёт, победитель | несколько раз за схватку, по событию | да (задержка ≤ 1 с) |
| **Таймер** | **непрерывно**, каждые доли секунды | **только если REST отдаёт текущее время** |

REST-ответ — это то, что лежит в базе. Тикающее время в базу обычно не пишут каждые 100 мс:
сохраняют события «старт», «стоп», итоговую длительность. Тогда `GET /fight/...` вернёт
**последнее сохранённое** значение — в эфире таймер будет стоять или прыгать. Живое время
табло получает потоком — через Mercure (или UDP).

**Это предположение, а не факт**: в спецификации нет описания ответов. Поэтому сейчас сервис
берёт таймер из REST, а Mercure не подключён.

## Как проверить на реальной Arena (5 минут)

1. **Есть ли живое время в REST.** Во время идущей схватки дважды с интервалом в пару секунд:
   ```bash
   curl http://<сервис>:8090/raw/fight/<mat_id>
   ```
   Если какое-то поле времени меняется вместе с табло → **Mercure не нужен**, достаточно указать
   путь к этому полю в `mapping.json` (`"timer": [...]`).

2. **Если не меняется — посмотреть, что слушает табло.** Открыть табло Arena в браузере →
   DevTools (F12) → Network → фильтр `mercure` (тип *EventStream*). Там видно:
   адрес хаба, параметры `topic=…` и сами сообщения во вкладке *EventStream*/*Messages*.

3. **Получить токен и подписаться вручную:**
   ```bash
   curl http://<сервис>:8090/raw/api/json/client/local                      # id локального клиента
   curl http://<сервис>:8090/raw/api/json/scoreboard/mercuretoken/<eventId>/<clientId>
   curl -N -H "Authorization: Bearer <токен>" \
        "http://<arena>/.well-known/mercure?topic=<топик из шага 2>"
   ```

Пришлите адрес хаба, топики и 2–3 сообщения (особенно с таймером) — по ним подключение
пишется точно, а не наугад.

## Как это будет встроено в сервис

```
                ┌─ REST-опрос (раз в 1 с) ─► ФИО, страна, вес, счёт, победитель ─┐
 Arena ─────────┤                                                              ├─► /vmix (один документ)
                └─ Mercure SSE (поток)    ─► таймер, период (+ счёт мгновенно) ─┘
```

- Подписка живёт в фоне того же контейнера, токен обновляется сам.
- Значения из потока накладываются на снимок по ковру/схватке.
- При обрыве потока сервис переподключается, а таймер временно берётся из REST — эфир не пустеет.
- Все значения проходят ту же очистку, что и остальные поля (только чистые строки).

## Запасной вариант без Mercure

Если REST отдаёт хотя бы **время старта и состояние** («идёт / пауза») и накопленное время,
таймер можно досчитывать в сервисе локально: `накоплено + (сейчас − момент старта)`.
Точность — доли секунды, но при паузах/коррекциях судьи возможен скачок до следующего опроса.
Mercure надёжнее, потому что это ровно то, что видит табло.
